# 一、本机状态与操作恢复

Clerk的草稿、回执、撤销日志、写锁和同步缓存只属于本机运行状态，不进入版本控制。
Git通过`rev-parse --absolute-git-dir`确定当前检出的元数据目录，在其下统一使用`clerk/`。
普通克隆通常对应以下布局，子模块和工作树的实际目录由Git决定：

```text
.git/clerk/
  batches/       待执行的临时草稿
  operations/    执行结果、批处理步骤及Git恢复信息
  sessions/      活动会话
  undo/          尚未完成的事务日志
  write.lock     本检出的写入互斥锁
  sync.stamp     远端查询缓存时间
  identity       本工作树的operator
  identity.lock  旧operator迁移互斥锁
```

活动会话放在Git公共目录的`clerk/sessions/`，由同一仓库的工作树共享；其余信息按工作树隔离。
没有Git元数据时，本机运行状态使用工作区的`.work/clerk/`；批处理草稿仍要求Git检出。
Git要求的钩子留在Git规定的钩子位置，不属于这次目录归并。

`clerk whoami`分别列出Git账号、人员表按邮箱归并的person和本机operator。
`clerk people list`查看账号到人员的映射，`clerk id <名字>`只改变本机operator，
不修改Git配置、不改变owners、认领者或已创建记录的发布者。多个Agent仍通过session区分活动范围。
operator按工作树隔离；新克隆不继承它，Git账号仍由该克隆有效的Git配置决定。

首次使用会将旧`layout.identity`指向的文件迁入`clerk/identity`，默认来源是`.work/identity`。
相同内容可合并，不同内容停止并保留双方。停止旧进程后检查两个文件，明确保留的值并移除旧文件，
再运行`whoami`。`layout.identity`现在只描述迁移来源，后续`id`统一写新位置。

## 1.1 回执的用途

`operation status --json`可查看数据、提交和推送阶段，批处理结果位于`batch`字段。
记录包含原始提交说明、修改文件摘要和批处理步骤，供`operation retry`只补做Git收尾。
提交中的`Clerk-Operation`编号用于识别提交已经产生、但进程尚未来得及更新本机回执的情况。

本机回执不再生成[工作区业务资料](../architecture/model.md)中的受管文件。共享追溯使用Git提交、
任务证据和日志；其他克隆不能依靠本机回执恢复操作。不提供把整个本机目录提交入库的流程。

## 1.2 接受结果与防重放

正式执行在撤销日志中先保存完整的待发布回执，再写事务接受标记。接受前中断时恢复业务文件；
接受后中断时保留业务，先将已接受回执发布到`operations/`，再清理事务日志。
写入或重试入口在持有写锁时完成恢复，快照读取不恢复尚未结束的事务。

草稿的独立标识保存在本机回执中。只有已接受的结果会消耗草稿，失败回滚与演练不会消耗。
提交或推送失败时草稿可能仍存在，但再次应用会被拒绝，应使用回执编号重试Git。
正式成功或Git重试成功后清理对应草稿。本机回执目前保留，不做自动清理；删除它会失去恢复依据。

## 1.3 升级与迁移

升级前停止旧版本Clerk进程，先处理能够完成的旧Git收尾。首次访问会将旧`clerk-batches`、
`clerk-operations`、`clerk-sessions`、`clerk-undo`、`clerk-sync.stamp`及旧写锁迁入新布局。
迁移检查旧、新写锁；不同内容的目标文件冲突时停止并保留现场，不覆盖已有状态。
旧撤销日志一并迁移，快照只报告待恢复，写入或重试负责恢复。

旧版受管回执会导入本机`operations/`中的`batch`字段，不更改已有Git恢复状态。
其他克隆的历史回执若没有本机执行记录，仅保存历史步骤，不凭空推断可重试的Git状态。
导入完成后，可将工作区原`.clerk/operations/`中的受管文件正常删除并提交；历史提交不改写。
迁移后的新操作不会再创建这个目录。后续不要让旧二进制继续向旧布局写入。
