# 设计要求

这份文档写给接手`clerk`后续完善工作的实现者，包括用户与自动化代理。它复述的是本项目一贯坚持的设计标准，不是一次性的任务说明。动手前先读完[model](<model.md>)与[declarations](<declarations.md>)，本文只讲“怎么做才算合格”。

## 一、总原则

### 1.1 一处事实，一处实现

同一个行为只允许存在一个实现，其余地方调用它。新增能力前先找现成的同类实现；找到了就合并，不要并排再写一份。

反面例子：过滤条件曾在字段旗标与表达式两处各解析一遍；日志目录曾在`[layout]`与种类声明里各写一份；短旗标表曾散落在帮助与解析两处。这些都是后来花时间收掉的债。

判断标准：改一个规则时，需要改的文件数应当是 1。如果需要改 2 处以上，说明抽象没做完。

### 1.2 声明优先

能在声明里表达的事实不要写进代码：路径、字段、编号形状、状态、迁移、动作、默认值、治理强度、模板。代码只做解释与执行。

声明里不写过程逻辑。`[[action]]`是“做什么”，不是“怎么编程”。

### 1.3 先归属，再动手

新增能力先回答它落在哪一层：

| 层 | 内容 | 典型落点 |
|---|---|---|
| 基础层 | 工作区标记、布局、词表、校验规则 | `workspace.toml`、`registry/` |
| 实体层 | 种类、字段、状态、编号 | `config/kinds/*.toml` |
| 行为层 | 迁移、动作、关系、视图 | 种类声明内的表 |
| 命令面 | 解析、帮助、输出、默认值 | [cli.rs](../../src/interface/cli.rs)、[help.rs](../../src/interface/help.rs)、[output.rs](../../src/terminal/output.rs) |

找不到归属时先补概念，不要在命令面里临时加分支。

### 1.4 一致性高于单条规则

同一份代码里，命名、错误措辞、输出形状、帮助格式必须一致。与某条局部习惯冲突时，以整体一致为准。

用户能感知的地方尤其如此：帮助页、错误消息、表格排版、默认行为，风格断裂比功能缺失更明显。

### 1.5 一次改一类事

一项改动只解决一类问题。修排序就只动排序，不顺手改帮助文案；改文案就只改文案，不夹带逻辑。

需要连带修改时，在提交正文写清范围与理由。

## 二、声明与代码的边界

### 2.1 适合放进声明的

| 事实 | 位置 |
|---|---|
| 目录与文件名 | `[layout]`、种类声明 |
| 字段、类型、必填、枚举词表 | 种类的`[[field]]` |
| 状态与迁移 | `[state]`、`[[transition]]` |
| 动作与处理器 | `[[action]]` |
| 视图与列 | `[[view]]` |
| 默认值 | `[commands]` |
| 治理强度 | `[[path]]` |
| 模板内容 | `.clerk/templates/*.md` |

### 2.2 必须留在代码里的

解析顺序、错误码、文件读写、哈希、排序算法、渲染排版。这些是机制，写进声明只会变成不可校验的自由文本。

### 2.3 校验放在加载期

声明里的错误必须在加载时暴露，不要等到执行某个命令才报。未知键、未声明的字段、未知动词、非法默认值、缺失模板，都属于加载期或`check`的职责。

错误消息写清缺什么、期望什么。不要写“配置有误”。

### 3.1 语言特性

用枚举表达闭集，用结构体表达成组事实，用泛型只在确实消除重复时使用。不要为了“看起来优雅”引入 trait、宏或泛型，也不要把明明不同的行为硬塞进一个泛型参数。

行为重复不需要泛型，需要合并实现。

## 四、命令面规则

### 4.1 解析

| 规则 | 要求 |
|---|---|
| 未知选项 | 报用法错误，退出码 2，不静默忽略 |
| 长写与短写 | 短写表唯一，一个字母只对应一个长写 |
| 合并短写 | 只允许开关合并；取值短写必须单独带值 |
| 否定 | `--no-<开关>`关闭一个开关，未知的`--no-x`报错；带值形式的未知选项同样报错 |
| 唯一前缀 | 命令与动词都支持，歧义时列出候选 |

### 4.2 默认值

`[commands."名字"]`与`[commands."名字.动词"]`给命令配默认行为，规则如下：

| 规则 | 要求 |
|---|---|
| 优先级 | 命令行 > 动词默认 > 命令默认 > 视图声明 > 内建缺省 |
| 布尔`true` | 打开开关 |
| 布尔`false` | 不设置；取消默认用`--no-<开关>` |
| 取值项 | 命令行显式给值即覆盖 |
| 危险项 | `force`、`dry-run`、`request`、`help`、`version`、`root`不得做默认 |
| 校验 | 命令名、动词、字段名、选项名在加载时校验 |

### 4.3 帮助

帮助页是命令面的唯一说明书，必须由声明生成，不得手写第二份。

| 入口 | 输出 |
|---|---|
| `clerk`、`clerk help` | 总览：用法、内建命令、种类、全局选项 |
| `clerk help <名字>` | 该命令页 |
| `clerk <种类>` | 简短使用说明：用法、动词分组、示例，退出码 0 |
| `clerk <名字> --help` | 与该命令页相同 |

新增选项、动词、字段后，帮助页必须自动出现，不需要额外改文档。

### 4.4 错误

| 场景 | 要求 |
|---|---|
| 命令不存在 | 列出候选 |
| 动词不存在 | 指出“种类没有该动词”，并指向`clerk <种类>` |
| 工作区加载失败 | 报真实原因，不要退化成“未知命令” |
| 校验失败 | 指出文件、行、字段与期望 |

### 4.5 输出

| 规则 | 要求 |
|---|---|
| 表格 | 列宽按内容计算，表头与分隔线是默认行为 |
| 隐藏表头 | `--headers hide`只影响用户阅读的表格；`--json`、`--tsv`、`--csv`、`--md`不受影响 |
| 机器可读 | JSON统一为`count/columns/data`信封；`check`与`doctor`例外，报诊断结果 |
| 空结果 | 隐藏表头且无数据时输出为空；需要判断空集时用`--json` |
| 显示名 | `--display`把枚举键换成显示名，原始键用于脚本 |

### 4.6 退出码

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 检查发现问题，或读写失败 |
| 2 | 用法错误：选项、参数、声明不可用 |
| 3 | 取值不满足声明规则 |
| 4 | 状态冲突，例如前置字段为空 |
| 5 | 与远端不同步或请求基线已变化 |

退出码属于命令契约，脚本与钩子依赖它，改动要单独说明。

## 五、数据与校验

### 5.1 校验入口

`clerk check`是唯一的总校验入口。封存比对、字段类型、枚举取值、编号形状、主键唯一、关系两端、文档章节、元信息、链接、表格列数、索引对应，全部由它汇总。

单项检查可以有子命令，例如`clerk links check`，但规则实现只能有一份。

### 5.2 治理强度

`[[path]]`的等级决定行为：

| 等级 | 行为 |
|---|---|
| `sealed` | 哈希封存，手改需重新封存并留痕 |
| `validated` | 结构与取值校验；不属于文稿种类的 Markdown 检查链接与表格 |
| `tracked` | 内容按哈希追踪 |
| `generated` | 工具写出，不参与封存比对 |
| `free` | 不治理 |

未声明的路径完全自由。`scope`只列声明过的路径，新增受管目录时必须同时补声明。

### 5.3 数据改动

数据表、词表、声明都是数据改动。改完跑`clerk check`，涉及封存的按策略重新封存。

不要手改生成的表格与区块。确需绕过时用`clerk seal --note 理由`留痕。

## 六、模板与内容

模板内容写成文件，不写成配置里的字符串规则。以`.md`结尾的模板值按工作区相对路径读取，其余按内联文本处理。

当前统一的模板入口：

| 位置 | 读取方式 |
|---|---|
| `header` | 页面头部模板 |
| `heading` | 追加小节标题 |
| `template` | 行渲染模板 |
| `values` | `set`动作的值 |

模板占位符按场景固定：身份、时间、记录字段。新增占位符时先扩展`render`层的唯一实现，再让各处共用。

内容类文档由用户手写，工具只负责结构与校验。生成的现状页区块由数据渲染，用户只写区块外的正文。

## 七、迁移与兼容

声明形状可以改，但改完必须迁移工作区，删除旧键，不保留“兼容两套”的读法。

| 动作 | 要求 |
|---|---|
| 删旧键 | 同一次改动里从所有工作区删除 |
| 新增必填键 | 提供缺省值或迁移脚本 |
| 改类型 | 迁移后跑`check`与`render`，确认无改动 |
| 删代码 | 死函数、死键、死分支一并删除，不留注释封存 |

## 八、测试与验证

| 要求 | 说明 |
|---|---|
| 一条行为一个用例 | 用例名描述行为，不描述实现 |
| 回归用例 | 能触发被修复的问题 |
| 测试隔离 | 测试放在`tests/`或`#[cfg(test)]`，不留在业务路径 |
| 不依赖网络 | 测试不抓远端、不依赖外部服务 |
| 数据隔离 | 每个用例使用自己的临时目录 |

提交前至少运行：

```sh
cargo fmt --all -- --check
cargo clippy --offline --all-targets -- -D warnings
cargo test --offline
```

涉及工作区行为时，再在两个真实工作区运行`clerk check`与`clerk render`，并确认`render`无改动。

## 九、提交与协作

提交信息用英文约定式提交，首行`type(scope): summary`不超过72字符，正文至少两段，分别写改动与原因，并写清验证方式。正文只用ASCII。

只改格式的提交单独提交。

工作顺序：先设计，后实现。影响面大的改动先列出方案与取舍，等确认再动手。不要一边实现一边改设计。

修一处问题时，先问“同类问题还有几处”。同类的要一起收掉，否则下次还得回来。

## 十、文案与格式

| 项 | 要求 |
|---|---|
| 字符 | 只用键盘可直接输入的字符；箭头写`->`；不用emoji |
| 标点 | 中文正文用中文标点；代码、路径、URL内部保持半角 |
| 空格 | 英文与汉字之间不写空格 |
| 标题 | 一级用`一、二、三`加顿号；二级用`2.1`式编号 |
| 列表 | 条目名称与解释之间留空行 |
| 日期 | 中括号紧凑写法，例如`[20261031]` |
| 命名 | 简短、有语义；目录与文件不用空格与中文 |

帮助、错误、文档、提交信息都适用这套规范。

## 十一、验收清单

交付前逐项确认：

| 项 | 确认方式 |
|---|---|
| 行为只有一处实现 | 搜索同类调用，确认没有第二份 |
| 声明是唯一事实来源 | 改一处规则只改一个文件 |
| 帮助自动更新 | 新增选项后`clerk help`已包含 |
| 错误可行动 | 消息包含缺什么、期望什么 |
| 校验在加载期 | 写坏一个键，加载即报错 |
| 默认值可取消 | `--no-<开关>`与显式取值都有效 |
| 无死代码死键 | 删除或改用 |
| 工作区已迁移 | 两仓`check`通过、`render`无改动 |
| 测试覆盖行为 | 新用例能在旧实现上失败 |
| 文档同步 | `docs/`记录新规则 |
| 提交信息合格 | 类型、长度、正文段数、验证 |

## 十二、协作登记的维护边界

日志条目的元数据、切分和引用匹配集中在`log_entry`，写入与诊断共用字段引用校验。
会话集中在`session`，运行状态与受管事务分开；上下文只读取快照，不隐式续期。
文件地址的解析、定位、历史修复和Markdown链接生成集中在`references`，文稿校验
与维护命令共用解析器，渲染器只调用同一链接格式化函数。Git历史只提供可验证的
重命名证据，无法证明的候选不自动写入。工作区路径别名在发现时统一规范化。
