# Clerk协作工作流

- 日期：[20261101]
- 范围：文稿创建权限、安全同步、批量操作与Git收尾恢复

## 一、文稿创建与修改

契约的标题与短名是用户输入，编号由工具分配。复核的日期、时间由声明中的
`auto = "today"`与`auto = "clock"`生成，标题和短名仍由用户提供。

```sh
clerk --root library-workspace contracts new --slug reservation-record --title "预约记录数据" --file -
```

正文从标准输入读取，文件与索引在同一事务中写入。复核的正文须满足其必需章节声明。
同一秒内创建复核若产生重复主键，会拒绝并提示重试，不覆盖已有文稿。

| 字段规则 | 创建 | 后续修改 |
|---|---|---|
| `role = "status"` | 工具填入 | 工具维护 |
| 用户字段，`write = "create"` | 用户填入 | 拒绝修改 |
| 普通用户字段 | 用户填入 | 允许修改 |
| 文件名占位字段 | 按声明填入 | 固定，不隐式重命名 |

`slug`类型只接受ASCII字母、数字和中间的中线。文件名占位字段必须有输入或生成来源，
创建时不能是空值或包含路径分隔符。帮助标记工具维护、创建可填与可修改字段。
修改标题会同步文稿和索引，正文保持不变；本轮未提供短名重命名与跨文档链接迁移。

## 二、安全同步

```sh
clerk sync check
clerk sync fetch
clerk sync update
```

`check`比较已有引用，`fetch`抓取引用，`update`在安全条件满足时快进本地分支。
`update`要求当前是配置的分支，工作树、暂存区、未跟踪文件与子模块都没有改动，
且没有正在进行的合并、变基等Git操作。

| 分支状态 | `update`的结果 |
|---|---|
| 已同步 | 无修改 |
| 仅本地落后 | 抓取并快进 |
| 仅本地领先 | 保留本地提交，不推送 |
| 双方分叉 | 拒绝，交给用户处理合并 |
| 本地有修改 | 拒绝并列出修改，保留现场 |
| 抓取失败 | 拒绝，本次业务操作尚未执行 |

单次命令可以要求写前同步：

```sh
clerk tasks new --title "示例" --prefix APP --sync ff-only
```

同步在解释业务默认值和执行事务前完成，之后重新加载声明。演练不允许附加`--sync`，
需要先单独执行`sync update`。工作区维护者也可以在已有`[sync]`中设置：

```toml
[sync]
write_update = "ff-only"
```

缺省为`"refuse"`，保留原来的写前拒绝策略。自动快进不默认开启；请求捕获和演练
不触发策略快进。同步使用本机Clerk写锁，不自动暂存、变基、合并或更新子模块。
外部Git命令不遵守此锁，应避免同时修改同一个检出。

其他协作者仍可能在同步后再次推送。此时本地提交保留，由结果状态说明推送情况，
工具不会重新执行业务步骤，也不会自动合并共享数据。

## 三、批量工作流

重复使用的流程可声明为模板，用`workflow preview`预览、`batch --template`执行；
批次增删也可作为事务步骤。配置与示例见[任务接手与工作流模板](context-and-templates.md)。

### 3.1 执行入口

```sh
clerk batch --file workflow.toml --dry-run
clerk batch --file workflow.toml
clerk batch --file workflow.toml --json
```

工作流使用TOML保存顺序操作，不执行Shell。首版要求工作树干净，源文件可事先提交、
放在仓库外，或通过`--file -`从标准输入提供。单次执行只管理一个工作区。

每一步复用普通命令与请求重放的应用执行入口。整批共享一个写锁、撤销日志和封存边界，
按工作区策略最多提交一次、推送一次。关闭自动提交时，本地结果仍保留，需自行提交。

### 3.2 建立任务

以下示例要求工作区声明了对应任务字段、编号令牌和动作；先用`clerk help tasks`
核对本仓库的实际规则。

```toml
version = 1

[[step]]
kind = "tasks"
verb = "new"
as = "task"
values = { title = "编写预约实例契约", owners = "alice" }
tokens = { prefix = "ENG" }

[[step]]
kind = "tasks"
verb = "claim"
keys = ["@task"]

[[step]]
kind = "tasks"
verb = "start"
keys = ["@task"]

[[step]]
kind = "tasks"
verb = "brief"
keys = ["@task"]
body = "范围：编写契约。验收：字段与实例边界清楚。任务编号：${task.id}。"

[[step]]
kind = "logs"
verb = "add"
tokens = { title = "建立${task.id}", side = "alice" }
body = "任务已建立、认领并开始。"

[[step]]
verb = "render"
```

| 步骤键 | 说明 |
|---|---|
| `kind`、`verb` | 已声明种类及写入动词；只读动词不接受 |
| `as` | 新建步骤的唯一别名，只能引用前面的步骤 |
| `keys` | 对象主键；`@task`展开为该对象的完整主键 |
| `values` | 用户字段，值均为字符串，仍受权限和类型约束 |
| `tokens` | 编号令牌或动作输入，例如前缀、日志标题和维护方 |
| `body`、`file` | 正文文本或正文文件，两者只能选一个 |
| `force` | 显式确认需要强制开关的破坏性动词，缺省关闭 |

`${task.id}`读取前面新建步骤返回的字段，可出现在键、字段值、令牌与正文中。
`file`相对工作流文件目录解析；工作流从标准输入读取时，相对当前目录解析。
正文文件在执行前读入，步骤内的`file = "-"`不接受。字段里的业务路径仍相对工作区。

步骤使用显式参数与种类、编号声明的缺省值，不继承CLI的交互或输出默认值。
未声明的键、字段和动作输入会被拒绝。业务规则按顺序检查，后一项可以依赖前一项的结果。

### 3.3 收尾与回滚

对已有任务，使用真实编号作为`keys`，依次安排`finish`、`complete`、日志与`render`。
`complete`的`values`仍需提供真实证据路径与提交号。流程不会替用户决定验收结论。

执行结束后更新封存并运行共享的工作区检查。任何步骤或最终检查失败，整批恢复原文件；
演练执行相同规则后恢复，不保留编号登记、附件、回执或封存变化。
演练展示的编号不作永久预留，正式运行时可能不同。

成功执行将逐步结果与Git恢复状态统一保存到Git元数据的`clerk/operations/<操作ID>.toml`。
回执不入库，包含操作者、作者、基线、各步骤时间、对象和结果。接受事务前先暂存完整回执，
接受后发布；中断恢复先完成发布，避免业务已保存但缺少防重放依据。

## 四、结果状态与Git收尾

### 4.1 查询结果

```sh
clerk operation status
clerk operation status <操作ID> --json
```

不指定ID时查看本检出的最新回执。普通种类写命令的JSON结果增加`execution`；
结果中的`data`、`commit`和`push`分别说明三个阶段，不能仅凭一个退出码判断数据是否保存。

| 阶段 | 状态 |
|---|---|
| 数据 | `not_written`未执行、`rolled_back`已恢复、`saved`已接受、`pending`阶段中断、`unknown`恢复未确认 |
| 提交与推送 | `not_run`未执行、`pending`执行中、`skipped`策略跳过、`succeeded`成功、`failed`失败、`unknown`结果待核对 |

网络断开时，服务端可能已经接收推送，因此失败的推送保守记录为`unknown`。
工具保留Git原始错误，不修改TLS或证书校验设置。

### 4.2 重试Git阶段

```sh
clerk operation retry <操作ID>
clerk operation retry <操作ID> --json
```

重试只处理该操作的提交与推送，不重新创建对象、不重放业务动词。
工具核对记录的HEAD、文件摘要、分支及无关本地修改；条件不符就停止。
已提交的结果只重试推送，并可通过远端提交号识别已经成功的推送。

若数据状态尚未确认，或原操作因工作区已有修改而跳过自动提交，应人工检查；
重试入口不会替这些情形自动整理暂存区。远端分叉同样需要人工处理，禁止自动变基重放。
本机回执不随克隆迁移，跨机器追溯依赖Git提交、任务证据与日志；不能直接恢复另一克隆的操作。

## 五、边界

本地事务与网络推送没有共同原子性。Clerk保证在本地接受之前按原有撤销机制恢复文件，
接受之后保留结果并报告Git状态；进程中断恢复不等于断电或硬盘损坏恢复。
外部编辑器与Git进程不参与Clerk写锁，跨克隆编号竞争仍需同步与审核处理。
